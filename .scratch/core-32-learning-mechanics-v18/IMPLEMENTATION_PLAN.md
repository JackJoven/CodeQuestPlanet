## 1. 工作方式

先完成一节完整课程，再推广该工具。每节默认“构造 → 陌生迁移”，按知识点需要增加调试单元；工程实现仍覆盖正常、错误、边界与浏览器验收。保留原指令卡操作形式。

开发顺序按依赖排列；学生仍按 1–32 课学习。不一次把 32 课套入新模板，也不以更换标题和状态台文案作为交付。

每个工作包按独立、可审查的变更处理。进入下一个包前写明完成的课程、运行结果、仍未覆盖的内容。发现机制与规格冲突时，先在 PRD 记录决定，再同步代码与夹具，避免文档和实现各走一套。

## 5. 每节课的交付记录模板

每节完成后建立 lesson-XX-acceptance.md，至少记录：

1. 唯一核心能力；保留与新增的实际操作。
2. 构造与独立任务的内容版本和输入；说明是否需要必做修复，工程反例另列。
3. 参考有效方案与至少一个不同但语义正确的方案；可行方案受限时说明原因。
4. 针对本课典型误解的程序，以及为什么应该判失败或能力未达标。
5. 世界目标、核心结构、修复、迁移、解释各项实际结果。
6. 提示暴露、保存重载、旧进度迁移的结果。
7. 浏览器实际操作记录；截图用于呈现，不能代替执行证据。
8. 未完成事项、对应代码版本和下一步。
9. 使用的地形/机关、首次介绍方式、与知识点的因果关系；台阶/传送/时间等相关语义测试及与相邻课的玩法差异。

## 6. 避免再次“文档完成、机制未完成”

- PRD 中每个“学生可以”都要对应一个真实控件、一项执行语义和一个验收用例。
- “状态台、流程图、大地图已经出现”只算界面实现，不算知识点实现。
- 一个课程包只有参考答案成功不算通过；必须让典型误解方案暴露问题。
- 整体状态由逐课表汇总，不能用一批自动测试通过代替逐课状态。
- 交付给用户时优先给一节可从头到尾试玩的课，并说明验收了什么；用户反馈进入同一份 PRD 与实施表。
- 新机关同时交付执行规则、碰撞/状态、3D 与俯视图、学习轨迹及迁移夹具；只有模型、特效或背景变化不能标记机关教学已完成。
