# 01 · 第 17 课：成功采集才更新变量

Status: technical-acceptance-passed

依赖：现有 A/W 基础和第 19 课样板。只实施本课，完成后交付验收记录，不继续批量修改第 18–32 课。

## 1. 学习目标和学生操作

学生能用一个变量记录已成功采集的数量，区分“尝试一次”和“成功一次”，用实际事件解释为什么应在成功后加 1。

任务：“亲自编路线，让 count 和实际宝石数一直相同。”规则：“采到一颗才加 1；空采和重复采不加。”首屏同时指出：在“计数工具”页签设置规则，在“主程序”用原指令卡安排每一步；详细帮助、Python 和证据默认折叠。

学生亲自设置初值、更新时机和增量。首版模型：

```js
{ initialCount: null, updateOn: null, delta: null }
// initialCount: 0..3; updateOn: 'success' | 'attempt'; delta: 0..2
```

初值、时机、增量缺失才阻止运行；合法但不正确的选择必须执行。正确规则为从 0 开始、成功后 +1，但不要在构造草稿里自动连好所有槽。迁移保留学生已经定义的计数规则，主程序在新地图中重新从空白编排。

状态台并排显示“变量 count”和“实际宝石数”；前者来自 Python 变量事件，后者来自世界收集记录，不能两个读同一个 UI 数字。每次尝试显示成功/空采/重复及更新前后。不得增加长篇必读文字。

## 2. 世界与固定任务输入

使用回收港环形栈道、收集站、空采实验点和计数闸门。保持清楚可见的两个区域，采用已知台阶和固定桥，不引入传送或额外时间规则。**每一步移动、转向、采集尝试、计数检查和过门都由学生用原指令卡编排**；程序生成器不得插入固定导航、隐藏路线或替学生补齐终点动作。

可作为 guided 坐标基准：起点 (2,2)，A=(4,2)、B=(6,2)、C=(6,5)、空站 E=(2,5)，环形连接这些站，闸门设在终端支路。固化合法地面和导航路线；复制/旋转后先检查台阶边仍相连。地图不能用几行窄条充当完整舞台。

| 工程夹具 | 尝试顺序 / 初始宝石 | 正确 count 轨迹 | 期望 |
|---|---|---|---|
| 构造 G | A、E、A、B；A/B 有宝石 | 0→1→1→1→2 | 4 次尝试、2 次成功，计数检查通过，开门到终端 |
| 独立 T1 | 新布局，E、A、A；仅 A 有宝石 | 0→0→1→1 | 3 次尝试、1 次成功 |
| 独立 T0 | 独立空站布局，E、E；没有宝石 | 0→0→0 | 0 次成功，合法零结果，不能要求至少收一颗 |
| 独立 T3 | 新布局，C、A、B、E、C；A/B/C 有宝石 | 0→1→2→3→3→3 | 5 次尝试、3 次成功 |
| 错误规则 R | 任一含成功、空采和重复的布局，使用 attempt +1 | 变量随每次尝试增加 | 合法运行到计数检查；变量与世界数产生可见差异，闸门拒绝 |

学生必做流程只有构造 G 和一张未受强提示影响的独立迁移（首张 T1）；T0、T3 和错误规则继续用于自动验证或完成后的可选练习。构造与迁移的完整语义指纹应不同，不能只是改标题和 variant 编号。强提示污染当前迁移后，换用另一张等价迁移图重新验证。

## 3. 最小运行器扩展的确定契约

沿用 `collect()` 原有失败即停止的行为。**只为本课新增 `try_collect()`**，用于观察失败尝试，不让失败终止整个实验：

- 返回 Python True/False；当前位置有尚未收集宝石时成功一次，收集记录增加一颗。
- 空格或重复采集返回 False，宝石状态不变，不抛运行异常。
- 每次尝试推进一拍，不扣能量；成功不得又被 collect 事件重复推进一拍。
- 记录 `collect-attempt`，含 eventId、坐标、success、reason（collected/empty/already-collected）、worldCountBefore/After。
- 不在 JavaScript 内替学生更新 count。Python 中的赋值产生现有 variable 事件，再由评估器关联本次 attempt。

生成代码的实质必须为学生选择的更新规则，例如：

```python
count = 0
# 路线和尝试都来自学生放入的原指令卡。
move()
move()
collected = try_collect()
if collected:
    count = count + 1
# 后续每张“采集尝试”卡沿用同一条学生规则。
check_count(count)
# 通过检查才打开闸门；学生还要继续放入过门到终端的移动卡。
```

错误的 attempt 时机生成无条件加法。学生修改初值/增量必须反映在 Python 中。首版可展开任务尝试序列，以免同时教授列表遍历；更新规则只在学生模型中定义一份，由生成器复用。

增加本课 `check_count(value)` 辅助 API：比较实参、世界真实成功数以及该任务应完成的成功数；三者符合才开启本课计数门，否则记录 count-check 拒绝并安全停止。不要按模型选项猜世界结果。门作为 `terrain.gates` 的 `kind:'count'` 新类型，普通闩锁门继续默认 `kind:'switch'` 且必须有有效 switchId。计数门只能由检查成功打开，复位关闭；3D、俯视图和碰撞均读取同一个 gates 状态。

`check_count` 只能验证结果并开门，不能把 count 改成答案。任务目标除检查通过外还要实际走过门到终端，防止只有状态文字变化。所有失败都保留前面的事件。

这两个 API 的开放范围只限第 17 课对应 allowedFunctions/任务规则，旧课程行为保持兼容。runtime 属于共用代码，此扩展完成后要独立复查，不能仅改 UI 或判定。

## 4. 本课概念有效解与能力门

世界结果：真实成功数符合任务要求、计数检查成功、角色到终端、程序没有尾部错误。

概念证据：初始化为 0；每个成功 attempt 后恰有一次由前值加 1 的实际变量更新；失败 attempt 后无 count 增量；更新后的 count 与世界成功数逐次相等。只在结尾赋 count=目标数、初值=目标且增量 0，即使碰巧世界过关也不是概念有效解。

学生无需完成固定修复或解释表单。错误规则运行、空采、重复采集和零结果仍保存为工程证据；需要帮助时可用实际 before/after 指出首次差异，但它不是本课能力门的第三阶段。

掌握门：构造图真实执行正确计数规则并走过计数门 + 同一更新规则在一张语义不同、未受强提示影响的独立迁移图再次成功。两阶段都必须由学生自己的卡片路线产生成功、失败尝试和变量事件；仅有世界采集成功、只通过零结果、结尾直接写目标数或参考路线字符串匹配均不成立。
