# PRD v0.1：AI 伴学式游戏编程创作平台

## 1. 产品定位

面向 `10-14 岁` 学生的自研游戏编程学习平台。

学生选择自己喜欢的游戏类型，在 AI 伴学引导下，通过修游戏、改规则、看代码、做作品，掌握事件、变量、条件、循环、函数、碰撞、调试等核心编程概念，并形成基础 AI 协作开发能力。

一句话：

> 让学生从游戏玩家，成长为能理解规则、修改逻辑、看懂代码、用 AI 协作创作小游戏的人。

## 2. 核心用户

| 用户 | 描述 | 核心需求 |
|---|---|---|
| 学生 | 10-14 岁，喜欢游戏，可能接触过 Scratch 或 AI | 想做自己的游戏，不想从枯燥语法开始 |
| 家长 | 关心 AI 时代孩子还要不要学编程 | 希望孩子不是玩游戏，而是学会创造和表达逻辑 |
| 运营/课程方 | 希望沉淀自研平台能力 | 需要可复用、可扩展、可持续迭代的核心资产 |

## 3. 要解决的问题

传统少儿编程存在几个断层：

| 断层 | 表现 |
|---|---|
| Scratch 到 Python 断层 | 图形化很热闹，文字代码突然变枯燥 |
| 兴趣到能力断层 | 学生会玩，但不知道游戏规则背后的逻辑 |
| AI 到学习断层 | 学生会问 AI，但不知道如何描述、检查和修正 |
| 课程到作品断层 | 学了很多知识点，却没有真正可展示作品 |

本产品要解决的核心问题：

> 如何让学生在自学或少老师介入的情况下，通过游戏任务和 AI 伴学，逐步理解编程并完成作品。

## 4. 产品原则

| 原则 | 说明 |
|---|---|
| 学生主导 | 学生选择游戏类型、任务路径和作品方向 |
| 平台驱动 | 用任务、反馈、过关检测和作品系统推动学习 |
| AI 伴学 | AI 做提示、解释、调试和复盘，不做一键代写 |
| 规则先行 | 先理解游戏规则，再映射到代码 |
| 代码显性化 | 每条规则都能看到伪代码或真实代码 |
| 作品闭环 | 每个阶段都有可玩的成果，不只做练习题 |

## 5. 核心学习闭环

```text
选择游戏类型
-> 试玩坏掉/半成品游戏
-> 发现问题
-> 自己猜原因
-> 修改规则
-> 运行验证
-> 卡住时问 AI
-> AI 分级提示
-> 代码透视
-> 学生复盘
-> 保存作品
```

这个闭环优先级高于传统“老师讲解 -> 学生练习”。

## 6. 游戏类型策略

第一版不做全类型，只做 `2 条核心路线`：

| 路线 | 为什么选 |
|---|---|
| 射击类 | 适合讲输入、子弹、敌人、碰撞、得分、生成器、技能 |
| 平台跳跃类 | 适合讲移动、跳跃、重力、地面检测、金币、关卡、通关 |

底层教学目标统一，表现形式允许分叉。

示例：

| 编程概念 | 射击类表现 | 平台跳跃类表现 |
|---|---|---|
| 事件 | 按键移动飞船 | 按键移动角色/跳跃 |
| 变量 | 分数、子弹数、生命值 | 金币数、血量、跳跃次数 |
| 条件 | 子弹碰到敌人 | 玩家碰到金币/怪物 |
| 循环 | 定时生成敌机 | 刷新金币、移动平台 |
| 函数 | 发射子弹、释放技能 | 跳跃、冲刺、二段跳 |

## 7. 核心模块

### 7.1 任务地图

学生看到的不是传统课程目录，而是游戏化任务地图。

每个任务包含：

- 本关目标
- 可选游戏类型
- 当前知识点
- 半成品游戏
- 规则编辑器入口
- AI 伴学入口
- 过关检测
- 创意改造任务

### 7.2 游戏运行区

游戏运行区负责即时反馈：

- 运行
- 暂停
- 重置
- 显示坐标、速度、分数、血量等变量
- 显示通关/失败反馈

### 7.3 规则编辑器

核心表达结构：

```text
当 [事件] 发生
如果 [条件] 成立
就 [动作]
```

示例：

```text
当 子弹 碰到 敌人
如果 敌人生命值 > 0
就 敌人生命值 - 1
并且 分数 + 10
```

规则编辑器是平台核心资产之一，不建议完全照搬 Scratch/Blockly。

### 7.4 代码透视眼

同一条规则支持三层显示：

| 模式 | 用途 |
|---|---|
| 中文规则 | 让学生先理解逻辑 |
| 伪代码 | 建立代码结构感 |
| 真实代码 | 逐步过渡到 Python/JavaScript/GDScript 等语言 |

示例：

```python
if player.collides_with(enemy):
    if shield_on == False:
        hp = hp - 1
```

### 7.5 AI 伴学面板

AI 不是开放式聊天框，而是任务型伴学智能体。

AI 角色：

| 角色 | 做什么 |
|---|---|
| 任务向导 | 告诉学生下一步挑战 |
| 概念解释员 | 用游戏例子解释概念 |
| 调试伙伴 | 根据现象定位问题 |
| 代码翻译员 | 解释规则对应的代码 |
| 复盘教练 | 追问学生是否真正理解 |

AI 使用原则：

- 先让学生说猜测，再给提示。
- 默认只给方向，不直接给完整答案。
- 允许解释代码，不允许一键完成作品。
- 帮学生验证结果，而不是替学生做决定。

### 7.6 自动过关检测

平台要自动判断学生是否完成任务，降低老师依赖。

示例检测条件：

| 任务 | 检测 |
|---|---|
| 控制角色 | 角色坐标发生变化并到达目标 |
| 金币计分 | 吃金币后 `score` 增加 |
| 敌人碰撞 | 子弹击中敌人后敌人消失 |
| 自动生成 | 一段时间内生成多个敌人 |
| 技能释放 | 技能能触发且有冷却限制 |

### 7.7 学习复盘

每关完成后，学生填写或选择：

```text
这一关我学会了什么？
我修改了哪条规则？
这条规则对应哪段代码？
我问了 AI 什么？
我怎么验证 AI 的建议是对的？
```

这用于训练 AI 协作能力。

## 8. 非目标

第一版不做：

- 全学段覆盖。
- 信息学竞赛训练。
- 完整通用游戏引擎。
- 大型社区。
- 复杂老师后台。
- Unity/Godot 重型项目。
- AI 一键生成完整作品。

## 9. 成功指标

| 指标 | MVP 目标 |
|---|---|
| 学生完成第 1 课比例 | 80%+ |
| 学生能解释事件/坐标比例 | 60%+ |
| 学生自发尝试另一条路线比例 | 40%+ |
| AI 提示后能继续推进比例 | 70%+ |
| 家长认为不是单纯玩游戏比例 | 80%+ |

## 10. 第一版判断

最重要的假设：

> 学生可以通过“选择喜欢的游戏类型 + 修复规则 + AI 伴学 + 代码透视”，在少老师介入的情况下理解编程概念。

如果这个假设成立，再扩展后端、课程数量、作品系统和家长报告。
