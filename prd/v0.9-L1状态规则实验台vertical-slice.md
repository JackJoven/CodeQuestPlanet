# PRD v0.9：L1 状态规则实验台 Vertical Slice

Status: ready-for-agent  
Date: 2026-05-19

## 1. Problem Statement

当前项目已经沉淀了从 `v0.1` 到 `v0.8` 的完整产品思路：从 10-14 岁 6 课 MVP，逐步扩展到 L0-L2 课程天梯。但现有成品的主要问题是：

1. 页面更像课程地图、平台外壳和任务展示，而不是一个真正可学习、可试错的规则实验环境。
2. `v0.8` 已经明确指出，课程表依赖的“规则实验台”还没有真正成立。
3. 如果学生只能点击按钮推进，产品会退化成“点按钮过关”，不能证明学生理解了规则、状态和调试。
4. 如果继续同时铺开 L0-L2 的 52 节课程，第一阶段会被目录、导航和包装分散，无法验证核心学习机制。

因此，本版本不继续扩写课程天梯，也不重做完整平台，而是收敛到一个高质量 vertical slice：

> L1-08 状态小关：学生在规则实验台里，通过拼装多条规则、运行验证、观察状态、修复错误，完成一个会记住状态的单屏小游戏。

## 2. Solution

第一阶段聚焦 `L1 规则实验台 vertical slice`，打样课程选择 `L1-08 模块挑战：做一个会记住状态的小关`。

产品形态是一节少老师/自学优先的“游戏规则实验室”：

```text
学生进入一个俯视角单屏钥匙门机关房
-> 先试玩坏掉的小关
-> 观察没拿钥匙时门不开
-> 拼装规则让 hasKey 变成 true
-> 观察状态面板变化
-> 遇到门规则条件写反的必经 bug
-> 调试并修复门规则
-> 通关
-> 生成状态规则证据卡
```

本版本的成功不是“做出一个小游戏页面”，而是证明：

> 8-10 岁学生能通过规则卡片、多条规则列表、状态面板和受控 AI Coach，理解“游戏会记住我做过什么，后面的规则会根据状态决定结果”。

## 3. Version Goal

本版本只验证一件事：

> L1 阶段的规则实验台是否成立。

具体目标：

1. 学生能在一个单屏房间里实际移动角色、拿钥匙、碰门、碰危险物。
2. 学生能通过规则卡片拼出至少 3 条规则，并看到多条规则同时存在。
3. 学生能看到 `hasKey`、`doorOpen`、`hp` 的实时变化，且变化有高亮反馈。
4. 学生必须经历并修复一次门规则条件错误的 debug 节点。
5. 通关后生成并保存一张状态规则证据卡，包含规则链路、bug 修复和一句复盘。

## 4. Target User And Learning Mode

目标用户：

- 年龄：8-10 岁。
- 阶段：L1 规则游戏入门。
- 学习基础：能理解“当/如果/就”的日常语言，但不要求会写真实代码。
- 兴趣来源：喜欢小游戏，愿意通过试错理解规则。

学习模式：

- 主模式：少老师/自学优先。
- 兼容模式：老师课堂带着上也能用。

这意味着页面必须自己提供下一步路径，不能默认老师解释全部概念。

## 5. User Stories

1. As a student, I want to enter one clear lesson instead of a huge course map, so that I know what I should do now.
2. As a student, I want to move a character in a small room, so that I can test rules immediately.
3. As a student, I want to try touching the door before getting the key, so that I can observe the initial problem.
4. As a student, I want to see that the door does not open when `hasKey` is false, so that I understand state affects results.
5. As a student, I want to touch the key and see `hasKey` change, so that I know the game remembers what I did.
6. As a student, I want the changed state to highlight visually, so that I notice the important learning moment.
7. As a student, I want to assemble a rule from cards, so that I can focus on logic rather than syntax.
8. As a student, I want to choose from some wrong cards too, so that I must think instead of matching an obvious answer.
9. As a student, I want to see all rules in one list, so that I understand how one rule changes state and another rule reads it.
10. As a student, I want to see whether each rule has triggered, so that I can connect rules to game events.
11. As a student, I want to run the game after changing rules, so that I can verify my idea.
12. As a student, I want to meet a required bug where the door still does not open, so that I learn to debug instead of only following steps.
13. As a student, I want to compare `hasKey` with the door rule condition, so that I can find the reversed condition.
14. As a student, I want to fix the door rule from `hasKey is false` to `hasKey is true`, so that I understand why the rule now works.
15. As a student, I want to touch a danger tile and see `hp` change, so that I understand another example of state.
16. As a student, I want AI Coach to ask guiding questions, so that I get unstuck without receiving the full answer immediately.
17. As a student, I want AI Coach to explain `hasKey` in simple language, so that I can say what state means.
18. As a student, I want AI Coach to point me back to the state panel during debug, so that I learn a repeatable debugging habit.
19. As a student, I want to complete the level only after the correct state chain works, so that the win is tied to understanding.
20. As a student, I want to generate a state rule evidence card, so that I can see what I actually learned.
21. As a student, I want to write or choose one reflection sentence, so that I can explain the state chain in my own words.
22. As a parent, I want to see the evidence card, so that I know the child was not only playing a game.
23. As a parent, I want the report to show the bug the child fixed, so that I can see debugging and reasoning.
24. As a teacher, I want a single focused lesson, so that I can run it in class without explaining the whole product roadmap.
25. As a teacher, I want the rule list and state panel visible, so that I can ask students to explain their reasoning.
26. As a product builder, I want this slice to avoid backend and real AI dependencies, so that I can validate the learning loop quickly.
27. As a product builder, I want the evidence card saved locally, so that the report page can show a real outcome without accounts.
28. As a future agent, I want the lesson decisions documented clearly, so that I can implement the slice without reopening big product questions.
29. As a future agent, I want clear non-goals, so that I do not accidentally rebuild the whole L0-L2 platform.
30. As a future agent, I want hard acceptance criteria, so that I know when the first version is truly done.

## 6. Core Learning Flow

The lesson should follow this exact learning path:

```text
1. Enter L1-08 状态小关
2. Read the goal: use state to make a key-door room work
3. Try the broken level
4. Touch the door before getting the key
5. Observe: door does not open, doorOpen remains false
6. Touch or inspect the key
7. Assemble rule 1: touch key + key not collected -> hasKey true and hide key
8. Run and verify: hasKey changes from false to true
9. Try the door again
10. Encounter required bug: key is obtained but door still does not open
11. Observe state panel: hasKey is true
12. Inspect door rule: condition is wrong
13. Fix rule 2: touch door + hasKey true -> doorOpen true and pass level
14. Test danger rule: touch danger + hp > 0 -> hp decreases and player bounces back
15. Complete the room
16. Generate state rule evidence card
17. Save evidence locally
```

## 7. Game Design

Game form:

- Top-down single-screen room.
- No platform physics.
- No shooting.
- No enemies in the first version unless they behave like a simple danger tile.

Objects:

| Object | Role |
|---|---|
| Player | Controlled by keyboard or touch controls |
| Key | Changes `hasKey` from false to true |
| Door | Opens only when `hasKey` is true |
| Danger tile | Reduces `hp` and bounces player back |
| Safe start point | Reset/bounce destination |

Core state:

| State | Initial | Meaning |
|---|---:|---|
| `hasKey` | false | Whether the game remembers that the key was collected |
| `doorOpen` | false | Whether the door has opened |
| `hp` | 3 | Player health for danger feedback |

Win condition:

```text
doorOpen is true
and player reaches or touches the opened door
```

Failure condition:

- First version does not need a hard fail screen.
- If `hp` reaches 0, reset player to the start and show a short learning hint.

## 8. Rule Lab Design

The rule lab uses limited card assembly, not free text editing.

Each rule has three slots:

```text
当 [event]
如果 [condition]
就 [action]
```

The first version must support multiple rules at the same time.

Required rules:

| Rule | Event | Condition | Action | Notes |
|---|---|---|---|---|
| Rule 1 | Player touches key | Key is not collected | Set `hasKey` true and hide key | Correct rule |
| Rule 2 | Player touches door | `hasKey` is true | Set `doorOpen` true and pass level | Starts wrong during debug |
| Rule 3 | Player touches danger tile | `hp > 0` | Decrease `hp` and bounce player back | Reinforces state |

Required distractor cards:

- `hasKey is false`
- `score > 10`
- `spawn enemy`
- `open door before key`
- `increase score`

Rule list behavior:

- Students can see all active rules.
- Each rule shows whether it has triggered.
- Each rule shows whether it is incomplete, ready, or recently triggered.
- The door rule begins with an intentionally wrong condition during the debug step.

## 9. Required Debug Node

The lesson must include one required debug node.

Bug:

```text
The student has collected the key.
The state panel shows hasKey: true.
The door still does not open.
```

Cause:

```text
The door rule condition is wrong.
It checks hasKey is false instead of hasKey is true.
```

Student task:

```text
Observe state panel
-> inspect door rule
-> notice condition mismatch
-> replace wrong condition
-> run again
-> door opens
```

Learning point:

> Debugging means comparing what the game remembers with what the rule is checking.

## 10. State Panel

The state panel only shows:

```text
hasKey: false / true
doorOpen: false / true
hp: 3 / 2 / 1 / 0
```

Do not show:

- score
- coordinates
- speed
- timer
- inventory list
- complex logs

Required interaction:

- When a value changes, highlight the changed row.
- For `hasKey` and `doorOpen`, visually show the direction of change, such as `false -> true`.
- The debug hint should point students back to this panel.

## 11. AI Coach Mock

First version uses a controlled AI Coach mock, not a real model.

Coach behaviors:

| Type | Example |
|---|---|
| Observation prompt | Try touching the door before getting the key. What changed? |
| State explanation | `hasKey` is the game's memory. false means not yet, true means already. |
| Debug question | You can see `hasKey` is true. Which condition is the door rule checking? |
| Reflection prompt | Use one sentence to explain why getting the key changes what happens at the door. |

The coach must not:

- Write full answers automatically.
- Complete the rule list for the student.
- Act like an open chat product.
- Depend on network or model access.

## 12. Evidence Card

The lesson exit is a state rule evidence card, not only a success modal.

Evidence card should include:

```text
My level: Key-door state room

State chain I fixed:
1. Touch key -> hasKey changes from false to true
2. hasKey is true -> touching door changes doorOpen to true
3. Touch danger -> hp decreases and player returns to safety

Bug I fixed:
The door did not open after I got the key.
The cause was the door rule checking the wrong condition.
I changed hasKey is false to hasKey is true.

What I learned:
The game can remember what I did, and later rules can use that memory.
```

Persistence:

- Save the card to local storage.
- No account system.
- No cloud sync.
- The existing report surface may later read this saved evidence.

## 13. Implementation Decisions

1. Build this as a dedicated L1-08 vertical slice first, rather than extending the existing generic course runtime.
2. Keep the implementation dependency-free: static HTML, CSS, JavaScript, and Canvas.
3. Do not introduce Phaser, React, build tooling, backend services, or real AI in this version.
4. Reuse the visual identity where useful, but make the experience feel like a focused game rules lab.
5. Default the primary learning entry to L1-08 instead of L0-01 during this validation phase.
6. Keep the 52-lesson L0-L2 map as roadmap context, not as a promise that every lesson is currently complete.
7. Split the implementation into simple deep modules:
   - Game world state and Canvas runtime.
   - Rule card selection and rule list state.
   - Rule evaluator that applies active rules to game events.
   - State panel change detection and highlighting.
   - Guided learning/debug step controller.
   - Controlled AI Coach response map.
   - Evidence card generation and local persistence.
8. The rule evaluator should be isolated enough that it can be tested without Canvas.
9. The evidence card serializer should be isolated enough that the report page can read it later.
10. UI copy should avoid broad marketing claims and keep the student focused on the current rule/state/debug task.

## 14. Testing Decisions

Testing should focus on external behavior, not implementation details.

Good tests for this slice verify:

1. Applying the key rule changes `hasKey` from false to true.
2. The door does not open when the door rule condition is wrong.
3. The door opens after the condition is corrected.
4. Touching danger decreases `hp` and bounces the player back.
5. State panel output matches the actual world state.
6. The evidence card includes the fixed rules, bug record, and reflection.
7. Saved evidence can be loaded back from local storage.

If a test harness is added later, prioritize tests for:

- Rule evaluator.
- State transitions.
- Evidence card generation.
- Local persistence.

Manual browser acceptance is acceptable for the first static prototype, but the rule evaluator should be kept small and pure enough for future automated tests.

## 15. Acceptance Criteria

The first version is done only when all five hard criteria pass:

1. A student can move a character in a single-screen room and interact with key, door, and danger objects.
2. A student can assemble at least 3 rules from cards and see those rules together in a list.
3. The state panel shows `hasKey`, `doorOpen`, and `hp` live, with visible highlight on changes.
4. The student must encounter and fix the required reversed-condition door bug.
5. Completion generates and locally saves a state rule evidence card with rule chain, bug fix, and reflection.

## 16. Out Of Scope

This version explicitly does not include:

- Real AI model integration.
- AI Gateway.
- User accounts.
- Cloud save.
- Full parent report system.
- Complete work portfolio.
- 52 complete L0-L2 lessons.
- Phaser migration.
- React migration.
- Free-form text rule editor.
- General-purpose game engine.
- Shooting route.
- Platform jumping route.
- Backend APIs.
- Teacher/admin dashboard.
- Community or sharing features.

## 17. Risks And Tradeoffs

| Risk | Why It Matters | Mitigation |
|---|---|---|
| Still feels like clicking cards by instruction | Student may not understand state | Include distractors and required debug node |
| Debug is too hard for 8-10 岁 | Student may get stuck | Use state panel highlight and AI Coach guiding questions |
| UI becomes too busy | Rule list, game, state panel, coach can compete | Keep state panel to 3 values and hide nonessential metrics |
| Evidence card becomes formulaic | Parent value may feel fake | Include actual triggered rules and the specific bug fix |
| Dedicated page diverges from course system | Later integration may require work | Treat it as a vertical slice and port patterns only after validation |

## 18. Further Notes

This PRD intentionally narrows the product after `v0.8`.

The long-term L0-L2 route still stands as direction:

```text
L0: 让作品回应我
-> L1: 我会用规则实验台做单屏小游戏
-> L2: 我会做玩法原型、系统设计、代码过渡和毕业项目
```

But first implementation should prove the middle step:

> Can the rule lab make a child understand state through play, rules, debugging, and evidence?

If this slice works, future work should expand sideways:

1. Add more L1 rule lab lessons.
2. Generalize the rule evaluator and evidence card model.
3. Feed completed evidence into the report page.
4. Only then revisit L0-L2 course map completeness.
