# PRD v1.0：Signal Runner 3D 编程作品节点

Status: draft  
Date: 2026-06-09

## 1. Problem Statement

项目已经从旧的 L0-L2 课程门户和规则实验台方向，转向 `Signal Runner Node`：一个面向 12-14 岁零基础学生的 3D 闯关式编程作品节点。

旧 `v0.6 全学段 AI 开发能力课程体系` 的主要问题是：

1. 范围过大：同时讨论 6-8、8-10、10-14、14-17、17+，容易把当前产品拉回全学段路线图。
2. 年龄定位偏宽：旧主线写作 `10-14 岁`，但当前 3D 空间、运行日志、函数复用和综合调试更适合 `12-14 岁`。
3. 技术形态不匹配：旧文档仍围绕 `2D 游戏 MVP`、`Phaser`、`规则 DSL` 和 `AI 伴学`，当前实现是静态网页、Three.js 3D 场景、指令编排、单步运行和日志反馈。
4. 学习证据不匹配：旧评价强调规则、变量、AI 协作和作品报告；当前更需要证明学生理解程序执行、空间路径、失败原因和调试过程。
5. AI 权重需要后移：零基础阶段不应把 AI 协作作为主卖点，应先建立“我能读任务、排指令、运行、看日志、修错”的编程基本功。

因此，本版本不再扩展全学段课程体系，而是收敛为：

> 12-14 岁零基础学生通过 6 节 3D 信标探测员任务，理解编程的基础概念和调试方法，并完成一个可展示的 3D 编程作品节点。

## 2. Solution

Signal Runner 的学习形态是一个 3D 任务编程环境：

```text
观察 3D 地图
-> 读任务目标
-> 预测信标探测员路线
-> 点击指令组成程序
-> 运行或单步执行
-> 看信标探测员行为和运行日志
-> 定位错误并修改程序
-> 完成关卡
-> 生成作品证据
```

第一版只做 6 节课：

1. 启动巡航：序列
2. 路径调试：转向与日志
3. 危险传感器：条件判断
4. 压缩重复：循环
5. 路线函数：函数与复用
6. 三塔同步：综合调试作品

本版本的成功不是“做出更漂亮的 3D 地图”，而是证明：

> 12-14 岁零基础学生能通过 3D 空间任务，真正理解程序是按顺序执行的、失败可以通过日志定位、重复可以被循环压缩、稳定动作可以被函数命名复用。

## 3. Version Goal

本版本只验证一件事：

> Signal Runner 是否能成为 12-14 岁零基础学生理解编程的第一套 3D 作品节点。

硬目标：

1. 学生能在 3D 地图中读懂任务目标和信标探测员当前位置。
2. 学生能用指令库编排程序，而不是直接输入真实代码。
3. 学生能运行和单步执行程序，并看到信标探测员行为。
4. 学生能用运行日志定位至少 3 类失败：撞墙、空采集、上传位置错误。
5. 学生能在第 3-5 关分别理解条件、循环、函数的实际作用。
6. 学生能在第 6 关完成综合作品，并说清关键程序为什么能成功。

## 4. Target User And Learning Mode

目标用户：

- 年龄：12-14 岁。
- 基础：零编程基础或只接触过 Scratch/图形化编程。
- 兴趣来源：喜欢 3D 游戏、任务闯关、信标探测员/机器人/科幻场景。
- 学习状态：愿意动手试错，但还不能直接进入文本代码项目。

学习模式：

- 主模式：少老师/自学优先。
- 兼容模式：老师课堂带着上也能用。
- 单课时长：45-75 分钟。
- 节点长度：6 节课组成一个完整作品节点。

不面向：

- 6-8 岁启蒙用户。
- 已经能写真实项目代码的高中进阶学生。
- 想学习全栈、数据库、部署、AI Agent 的用户。

## 5. Learning Logic Redesign From v0.6

### 5.1 年龄层重设

旧 v0.6：

```text
10-14 岁：AI 游戏编程主线
14-17 岁：真实应用与游戏开发
```

新 v1.0：

```text
10-11 岁：可作为上游预备，不作为当前主产品
12-14 岁：Signal Runner 主用户，零基础理解编程
15 岁以上：可进入真实代码和 AI 协作进阶
```

理由：

- 3D 空间任务需要方向、路径、抽象执行顺序和调试耐心。
- 12-14 岁更容易理解“我写的程序”和“信标探测员行为”之间的因果链。
- 这个年龄能开始接受伪代码和真实代码视图，但不需要一开始手写语法。

### 5.2 课程主线重设

旧 v0.6 主线：

```text
规则 DSL
-> 2D 游戏规则
-> AI 伴学
-> 作品报告
```

新 v1.0 主线：

```text
3D 任务目标
-> 指令编排
-> 程序执行
-> 运行日志
-> 单步调试
-> 代码结构化
-> 作品证明
```

### 5.3 概念顺序重设

旧顺序偏向游戏规则：

```text
事件 / 变量 / 碰撞 / 循环 / AI 协作 / 作品
```

新顺序偏向程序执行：

```text
序列
-> 方向与路径
-> 失败日志
-> 条件判断
-> 循环压缩
-> 函数复用
-> 综合调试
```

### 5.4 AI 定位重设

旧 v0.6 把 AI 伴学作为全学段核心能力。

新 v1.0 中，AI 暂时后置或降级为受控 Coach：

- 第一阶段不接真实 AI。
- 不做开放聊天。
- 不自动给完整答案。
- 只提供分级提示、调试追问和复盘问题。

### 5.5 评价证据重设

旧证据：

```text
作品 / 过程 / AI 协作 / 展示表达
```

新证据：

```text
程序执行成功
失败日志读懂
调试记录
代码结构压缩
最终作品卡
```

## 6. Concept Ladder

| 阶段 | 核心概念 | 学生要能说出的话 | 产品证据 |
|---|---|---|---|
| Lesson 01 | 序列 | 程序会从上到下一步一步执行 | 指令顺序正确后采集并上传 |
| Lesson 02 | 方向与调试 | 撞墙不是游戏坏了，是某一步方向错了 | 日志指出失败点，学生修改转向 |
| Lesson 03 | 条件 | `if` 不是装饰，它决定什么时候开盾 | 只在危险前开盾，能量保留 |
| Lesson 04 | 循环 | 重复动作可以用 repeat 表达 | 连续 move 被 repeat 替代 |
| Lesson 05 | 函数 | routeA 是给一段稳定路线起名字 | 主程序调用 routeA 两次 |
| Lesson 06 | 综合调试 | 程序要同时考虑路径、危险、采集和上传 | 三座信标全部采集并上传 |

## 7. Core Learning Flow

每节课都遵循同一套学习闭环：

```text
1. 进入当前任务
2. 阅读任务目标
3. 旋转/观察 3D 地图
4. 判断起点、信标、危险、中继站的位置关系
5. 从指令库选择允许指令
6. 组成主程序或 routeA
7. 先预测程序会怎么跑
8. 运行或单步执行
9. 观察信标探测员行为
10. 阅读运行日志
11. 如果失败，定位失败发生在哪一步
12. 修改指令顺序或结构
13. 再次运行验证
14. 过关后保存本关证据
15. 最终生成作品卡
```

关键要求：

- 每次失败都必须有学生能读懂的日志。
- 每关的“完成”不能只看程序是否跑完，还要看是否触达学习目标。
- 参考答案可以存在，但应被定位为“对照”，不是默认学习路径。

## 8. Course Design

### 8.1 Lesson 01：启动巡航

学习目标：

- 理解程序按顺序执行。
- 理解 `move()`、`collect()`、`upload()` 的先后关系。

任务：

```text
从起点出发，采集绿色信标，再到中继站上传。
```

错误设计：

- 提前 `collect()`：当前位置没有信标。
- 提前 `upload()`：信标探测员不在中继站。
- 少一步 `move()`：没有到达目标格。

出口证据：

```text
我知道 collect() 必须发生在信标探测员到达信标格之后。
```

### 8.2 Lesson 02：路径调试

学习目标：

- 理解方向、转向和路径。
- 学会根据失败日志修正程序。

任务：

```text
绕过阻挡，采集下方信标后上传。
```

错误设计：

- 撞墙。
- 转向方向错误。
- 路线绕过了信标。

出口证据：

```text
我能根据“撞墙”日志找出是哪一步方向错了。
```

### 8.3 Lesson 03：危险传感器

学习目标：

- 理解条件判断。
- 理解 `ifHazardShield` 只在前方危险时执行开盾。

任务：

```text
穿过危险格前开盾，保留能量完成上传。
```

错误设计：

- 不开盾直接穿危险。
- 每次都手动开盾导致能量浪费。
- 条件判断放错位置。

出口证据：

```text
我知道 if 的意思是：只有条件成立，动作才发生。
```

### 8.4 Lesson 04：压缩重复

学习目标：

- 理解循环表达重复模式。
- 从“能跑”过渡到“更清楚”。

任务：

```text
用 repeat 指令减少程序长度，同时完成采集与上传。
```

错误设计：

- 全部堆 `move()`，能跑但不清楚。
- repeat 次数不对。
- repeat 后忘记采集或上传。

出口证据：

```text
我能把三个连续 move() 替换成 repeat(3)，并证明结果没有变。
```

### 8.5 Lesson 05：路线函数

学习目标：

- 理解函数是给一段稳定动作命名。
- 理解主程序调用函数时，会执行函数里的指令。

任务：

```text
定义 routeA()，在主程序里调用它两次。
```

错误设计：

- 调用空函数。
- routeA 内容正确但主程序顺序错。
- 主程序重复写路线，不使用函数。

出口证据：

```text
我知道 routeA() 不是一句说明，它会执行函数里已经放好的路线。
```

### 8.6 Lesson 06：三塔同步

学习目标：

- 综合使用序列、转向、条件、循环和调试。
- 完成一个可展示的作品节点。

任务：

```text
采集 3 座信标，在能量耗尽前回到中继站上传。
```

错误设计：

- 漏采集。
- 路径过长导致能量不足。
- 危险格没有处理。
- 上传位置错误。

出口证据：

```text
我的日志证明三座信标都被采集，并且最后在中继站上传。
```

## 9. User Stories

1. As a student, I want to start from one clear 3D mission, so that I know what I should do now.
2. As a student, I want to rotate the 3D map, so that I can inspect the route before writing commands.
3. 作为学生，我希望清楚看到信标探测员、信标、危险格、障碍和中继站，从而明确任务目标。
4. As a student, I want a small command library, so that I can focus on logic instead of typing syntax.
5. As a student, I want to click commands into the program, so that I can build a program without keyboard friction.
6. As a student, I want to see code-like text, so that I can connect command blocks to real code later.
7. As a student, I want to run the program, so that I can see whether my idea works.
8. As a student, I want to single-step the program, so that I can find exactly where behavior changes.
9. 作为学生，我希望信标探测员的移动与指令顺序一致，从而理解顺序执行。
10. 作为学生，我希望任务失败时看到日志，从而知道失败原因可以被解释。
11. As a student, I want logs in plain language, so that I can debug without reading professional error messages.
12. As a student, I want the log to mention collision or wrong location, so that I can connect failure to the map.
13. As a student, I want to revise commands after failure, so that debugging feels like normal learning.
14. As a student, I want to compare my program with a reference only after trying, so that I do not skip thinking.
15. As a student, I want to learn `if` through a hazard tile, so that conditions solve a visible problem.
16. As a student, I want to learn `repeat` through a long straight route, so that loops feel useful.
17. As a student, I want to learn `routeA()` through repeated route segments, so that functions feel like naming a plan.
18. As a student, I want each lesson to unlock the next concept, so that I do not feel dumped into all commands at once.
19. As a student, I want the final mission to combine previous ideas, so that my earlier learning matters.
20. As a student, I want a final work card, so that I can show what I built and understood.
21. As a parent, I want to see more than a 3D game screen, so that I know the child is learning programming.
22. As a parent, I want the evidence card to show debugging, so that I know the child handled failure.
23. As a parent, I want age-appropriate goals, so that I do not expect full-stack development from a beginner.
24. As a teacher, I want one 6-lesson node, so that I can run it as a compact course unit.
25. As a teacher, I want consistent lesson structure, so that classroom pacing is predictable.
26. As a teacher, I want logs and code views visible, so that I can ask students to explain their reasoning.
27. As a curriculum designer, I want each lesson to target one concept, so that the node does not become a generic puzzle game.
28. As a product builder, I want the 3D view to be decoupled from logic, so that camera rotation never changes task results.
29. As a product builder, I want the command runner to be testable without Three.js, so that core learning behavior can be protected.
30. As a future agent, I want this PRD to replace the broad v0.6 route, so that implementation does not drift back to old L0-L2 scope.

## 10. Product Surface

The first product surface should keep the current Signal Runner layout:

- 3D mission map on the left.
- Mission goal and run controls near the programming area.
- Command library with only the commands needed for the current lesson.
- Program list for the main program.
- Optional `routeA()` board only when the function lesson needs it.
- Code view that mirrors the command list.
- Run log as the main debugging surface.
- Evidence card as the node exit.

Do not turn the first screen into a marketing landing page. The first screen should remain the usable programming mission.

## 11. Feedback And Evidence

### 11.1 Runtime Feedback

The runtime must expose:

- Current mission title.
- Current concept.
- Beacon progress.
- Energy.
- Shield state.
- Run state.
- Plain-language log.
- Success or failure reason.

### 11.2 Failure Logs

Logs should be written as student-facing debugging clues:

| Failure | Log Style |
|---|---|
|撞墙|撞到阻挡：当前位置和朝向是什么|
|空采集|采集失败：当前位置没有可采集信标|
|错误上传|上传失败：信标探测员不在中继站|
|漏采集|上传失败：还需要几座信标|
|能量耗尽|哪类动作导致能量耗尽|
|空函数|调用 routeA() 失败：函数里还没有指令|

### 11.3 Evidence Card

最终作品卡应包含：

```text
作品名：Signal Runner：三塔同步信标探测员

我用到的代码能力：
序列、条件判断、循环压缩、函数封装、综合调试

我修过的一个错误：
例如撞墙、漏采集、上传位置错误、没有开盾、调用空函数

我如何证明程序成功：
运行日志显示采集 3 座信标，并在中继站上传

我的复盘：
哪一段程序最关键，为什么
```

## 12. Implementation Decisions

1. 以 `signal-runner-node` 作为唯一主项目，不继续扩展旧课程门户。
2. 保持静态网页形态，优先支持直接用 Edge/Chrome 打开本地 HTML。
3. 3D 视图只负责可视化，不改变程序执行逻辑。
4. 地图拖拽旋转只改变相机视角，不改变坐标、方向、碰撞和任务判断。
5. 指令运行器应被视为核心学习模块：输入是命令序列，输出是信标探测员状态、日志、成功/失败结果。
6. 任务数据应继续数据化：每关声明标题、概念、故事、目标、允许指令、参考解。
7. 程序视图和代码视图应从同一份命令数据生成，避免展示和执行不一致。
8. 运行日志应成为调试主界面，而不是隐藏在开发者控制台。
9. 单步执行必须保留，因为它是从“玩关卡”转向“理解程序执行”的关键。
10. 参考答案可以保留，但未来应增加“先尝试再载入”的产品约束。
11. Evidence card 需要从静态说明升级为真实完成证据，逐步记录学生完成情况和调试过程。
12. 第一版不接入真实 AI；若加入 Coach，应使用受控提示库。
13. 后续如果要转向真实代码，应先加入伪代码/JS 对照，不直接替换当前指令编排。
14. 可考虑抽出深模块：
    - Mission model：关卡目标、地图、允许指令、参考解。
    - Command runner：执行命令、展开 repeat 和 routeA。
    - Failure reporter：把失败状态转成学生语言日志。
    - Evidence builder：根据完成记录生成作品卡。
    - View controller：控制相机、拖拽旋转和渲染节流。

## 13. Testing Decisions

测试重点应放在外部行为，而不是 Three.js 细节。

优先测试：

1. Lesson 01 的正确指令能采集并上传。
2. `collect()` 在非信标格会失败，并给出可读日志。
3. `upload()` 在非中继站会失败，并给出可读日志。
4. 撞墙时日志包含当前位置和朝向。
5. `ifHazardShield` 只在前方危险时开盾。
6. `repeat2` 和 `repeat3` 会展开为正确数量的 `move()`。
7. 空 `routeA()` 被调用时会失败。
8. `routeA()` 有内容时，主程序调用会执行函数内容。
9. 第 6 关完成条件要求采集 3 座信标并在中继站上传。
10. 相机拖拽旋转不改变信标探测员位置、方向或任务结果。

测试层次：

- 命令运行器：纯逻辑测试。
- 失败日志：输入失败状态，输出学生语言。
- Evidence builder：输入完成记录，输出作品卡字段。
- 3D 视图：只做轻量 smoke test，确认非空渲染和拖拽事件不报错。

## 14. Acceptance Criteria

第一版 PRD 对应的产品验收标准：

1. 6 节课都能从空进度开始完成。
2. 每节课只有当前所需指令，不提前暴露过多概念。
3. 学生可以通过运行和单步观察程序执行。
4. 每种常见失败都有学生能理解的日志。
5. Lesson 03 明确证明条件判断的作用。
6. Lesson 04 明确证明循环压缩的作用。
7. Lesson 05 明确证明函数复用的作用。
8. Lesson 06 需要综合使用至少 3 类已学能力。
9. 3D 地图可拖拽旋转，但不影响逻辑结果。
10. 最终作品卡包含代码能力、调试记录和成功证明。

## 15. Out Of Scope

本版本不做：

- 全学段课程体系。
- L0/L1 低龄启蒙。
- 旧规则实验台继续开发。
- 2D Phaser 路线。
- 真实自由代码编辑器。
- 复杂 3D 开放世界。
- 关卡编辑器。
- 用户账号。
- 云保存。
- 后端 API。
- 真实 AI 模型接入。
- AI Agent、RAG、评测系统。
- 数据库、部署、权限、商业化后台。

## 16. Risks And Tradeoffs

| Risk | Why It Matters | Mitigation |
|---|---|---|
| 3D 画面吸引注意但稀释学习 | 学生可能只玩视角和画面 | 每关必须有明确概念和出口证据 |
| 参考答案让学生跳过思考 | 学习退化为点按钮通关 | 参考答案作为对照，未来增加先尝试约束 |
| 地图旋转让方向更混乱 | 学生分不清视角和信标探测员朝向 | UI 和日志始终显示信标探测员真实朝向 |
| 日志太工程化 | 零基础学生读不懂 | 使用学生语言，并指向地图现象 |
| 循环和函数只像省步数 | 学生不理解结构化意义 | 强调“结果不变但程序更清楚” |
| 课程太短 | 6 课只能建立核心直觉 | 先验证节点，再扩展后续 6-12 课 |

## 17. Future Roadmap

如果 v1.0 验证通过，后续扩展顺序建议：

1. v1.1：强化调试证据，记录学生失败、修改、再运行过程。
2. v1.2：加入受控 Coach，不给答案，只给调试追问。
3. v1.3：加入更多 3D 任务节点，如巡逻、开关、能量管理、路径优化。
4. v1.4：加入伪代码到 JavaScript 的过渡层。
5. v2.0：进入真实代码项目，让学生把 Signal Runner 的概念迁移到小型 Web/游戏项目。

## 18. Further Notes

本版本不是对 v0.6 的小修补，而是一次主线替换：

```text
从：全学段 AI 开发能力路线图
到：12-14 岁零基础 3D 编程作品节点
```

一句话定位：

> Signal Runner 不是让学生背语法，也不是让 AI 替学生写代码；它让学生先在 3D 任务里看见程序如何执行、如何失败、如何被调试，最后能解释自己写出的程序为什么成功。
